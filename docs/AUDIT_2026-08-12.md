# PART A — Static audit (as-of first read)

## Executive summary

The codebase is **well-architected and largely production-ready**. Authorization is enforced server-side via a real RBAC layer (`requirePermission`), prices are recomputed on the server at checkout (client totals are never trusted), payment webhooks are HMAC-verified with timing-safe comparison and idempotency keys, TOTP secrets are encrypted with AES-256-GCM, and the outbox worker has proper retry/backoff/dead-lettering. Secrets are correctly git-ignored; the Docker image runs as a non-root user.

**However, there is one HIGH-severity authentication bypass that must be fixed before launch** (guest order-tracking cookie is signed with an unkeyed hash → fully forgeable → customer PII exposure), plus a small set of medium issues around brute-force resistance and upload-ownership. None of the blockers are architectural — all are localized fixes.

### Verdict: **Not launch-ready as-is.** Fix F1 (blocker) + F2–F4 (strongly recommended), then ship.

| # | Severity | Area | Issue |
|---|----------|------|-------|
| F1 | 🔴 **High** | Auth / Privacy | Order-tracking access cookie signed with keyless SHA-256 → forgeable, bypasses OTP |
| F2 | 🟠 Medium | Auth | No rate-limit on OTP **verification** attempts (login + track) → 6-digit brute force |
| F3 | 🟠 Medium | Auth / Abuse | No rate-limit on order-tracking OTP **issuance**; `submitBankTransferReceipt` unauthenticated + unthrottled |
| F4 | 🟠 Medium | Uploads | `completeUpload` / presign trust caller-supplied key & MIME; no ownership binding |
| F5 | 🟡 Low | Rate-limit | `x-forwarded-for` trusted verbatim → IP-based limits spoofable if proxy misconfigured |

## Detailed findings

### F1 — 🔴 HIGH: Forgeable order-tracking access cookie (auth bypass → PII exposure)

**Files:** [`modules/messaging/track-otp.ts:154`](modules/messaging/track-otp.ts:154) (`grantTrackAccess`/`hasTrackAccess`), gated at [`app/[locale]/(shop)/track/[orderNumber]/page.tsx:15`](app/[locale]/(shop)/track/[orderNumber]/page.tsx:15)

The guest order-tracking gate protects a page that reveals order contents, shipping address, phone, and WhatsApp number. Access is granted by a cookie:

```
payload = `${orderNumber}:${email}:${expiryEpoch}`
signed  = sha256(payload)          // hashToken() — NO secret key
cookie  = `${signed}:${payload}`
```

`hasTrackAccess` re-computes `sha256(payload)` and compares. Because the "signature" is a plain unkeyed hash, **anyone can compute a valid cookie themselves** without ever passing the email-OTP step:

1. Attacker sets `payload = "<orderNumber>:whatever@x.com:9999999999999"`.
2. Computes `sha256(payload)` (public function, no secret).
3. Sets `aks_track_access` = `sha256(payload):payload`.
4. `hasTrackAccess` accepts it → full order PII disclosed.

Order numbers are generated server-side and may be partly guessable/enumerable, widening exposure. The OTP flow that precedes this (`issueTrackOtp`/`verifyTrackOtp`) is entirely bypassed.

**Fix direction:** sign with a keyed MAC — `crypto.createHmac('sha256', process.env.AUTH_SECRET)` — or issue a short signed JWT / server-side session row instead of a self-verifying cookie. Compare with `timingSafeEqual`. This is a ~5-line change but is a launch blocker.

### F2 — 🟠 MEDIUM: OTP verification not rate-limited (brute force)

**Files:** login path [`auth.ts:92`](auth.ts:92) (`verifyEmailOtp`), [`modules/auth/otp.ts:69`](modules/auth/otp.ts:69); track path [`modules/messaging/track-otp.ts:127`](modules/messaging/track-otp.ts:127)

OTP **issuance** is rate-limited (5/email/hr, 20/IP/hr — [`modules/auth/rate-limit.ts`](modules/auth/rate-limit.ts)), but **verification attempts are not**. The code is 6 digits (10⁶ space) with a 10-minute TTL and only one active code at a time. Nothing caps failed `authorize()` submissions, so a staff account (or a guest tracking session) can be brute-forced by volume. Failed attempts are logged to `signInAttempts` but never counted against a threshold at verify time.

**Fix direction:** count recent failed `otp_invalid`/`2fa_invalid` rows per email (and per order for tracking) and lock out after N (e.g. 5–10) within the TTL window; you already have the log table to do this cheaply.

### F3 — 🟠 MEDIUM: Unauthenticated / unthrottled guest write paths

- **`submitBankTransferReceipt`** ([`modules/payments/bank-transfer/submit-receipt.ts:9`](modules/payments/bank-transfer/submit-receipt.ts:9)) is a `"use server"` action with **no auth and no rate limit**. Any caller can attach a receipt asset to **any order number** they know and create a `PENDING` payment row. Impact is bounded because an admin manually verifies (F-verify enforces `money.verify_payments`), but it enables spam/DoS of the verification queue and lets a stranger attach arbitrary images to someone's order. Add throttling + confirm the order number belongs to the submitting guest session/email.
- **`issueTrackOtp`** ([`track-otp.ts:70`](modules/messaging/track-otp.ts:70)) sends email with no rate limit → can be abused to spam a customer's inbox (and burns Resend quota). `resolveOrderEmail` also distinguishes "order not found" implicitly via the single error string (acceptable), but pair issuance with the same rate-limit table as F2.

---

### F4 — 🟠 MEDIUM: Upload finalize trusts caller-supplied key & MIME

**Files:** [`app/api/assets/presign/route.ts`](app/api/assets/presign/route.ts), [`app/api/assets/complete/route.ts`](app/api/assets/complete/route.ts), [`modules/platform/assets/r2.ts:126`](modules/platform/assets/r2.ts:126)

`/api/assets/complete` requires *a* session but not the *right* session: any logged-in user (including a `CUSTOMER`) can call `completeUpload({ key, mime })` for **any R2 key**, and the stored `mime` is caller-asserted (not sniffed from bytes — `sharp` only reads dimensions). Presign lets guests upload arbitrary `image/*`. Combined, a user can register asset rows pointing at keys they don't own or with a spoofed MIME. Low blast radius today, but bind uploads to a per-session key prefix (e.g. `uploads/<userId|anonId>/…`) and verify the finalizer owns the key; consider content-type sniffing on finalize.

### F5 — 🟡 LOW: `x-forwarded-for` trusted verbatim

**File:** [`modules/auth/sessions.ts:79`](modules/auth/sessions.ts:79) (also `modules/tryon/actions.ts:131`)

`clientIpFromHeaders` takes the first `x-forwarded-for` entry with no trusted-proxy allowlist. If the app is ever exposed without a proxy that *overwrites* XFF, the IP-based OTP limit (F2/F3) is trivially bypassed by spoofing the header. Ensure the edge (Cloudflare/nginx) strips inbound XFF and sets a trusted client-IP header; document the assumption.

### F6 — 🟡 LOW: No webhook timestamp freshness check

**Files:** [`app/api/webhooks/safepay/route.ts`](app/api/webhooks/safepay/route.ts), [`modules/payments/providers/safepay/verify-signature.ts`](modules/payments/providers/safepay/verify-signature.ts)

Signature verification is correct (HMAC-SHA256 over `timestamp + "." + body`, `timingSafeEqual`). The `X-SFPY-TIMESTAMP` is used in the MAC but never checked for recency, so a captured valid webhook could be replayed. The idempotency key on `payments` prevents double-processing of the *same* event, which mostly neutralizes impact — but add a tolerance window (e.g. reject > 5 min skew) as defense-in-depth.

### F7 — 🟡 LOW: Failing test from shared-DB pollution + schema drift

**File:** [`modules/discounts/discounts.test.ts:135`](modules/discounts/discounts.test.ts:135)

The assertion `discountBreakdownSnapshot.applied[0].discountId === discountId` fails because `evaluateCheckoutDiscounts` matched an **older `WELCOME15` row left in the shared test DB** (received uuid has an earlier timestamp than the one just inserted). Production is safe — the real schema has `uniqueIndex("discounts_code_uidx")` ([`packages/db/schema/discounts.ts:67`](packages/db/schema/discounts.ts:67)) that forbids duplicate codes — but the test-only `ensureDiscountsSchema()` helper evidently doesn't recreate that index, so dup rows accumulate when a prior run's `afterAll` cleanup is skipped. **This is a CI-reliability/test-hygiene issue, not a product bug.** Fix: truncate in `beforeAll`, or run integration tests against an ephemeral DB, and keep test-setup helpers in sync with migrations.

### F8 — 🟡 LOW: Checkout validation N+1 & DB-backed rate limiting

- [`modules/checkout/validate.ts:134`](modules/checkout/validate.ts:134): the per-line loop issues a separate `measurementFlowSessions` query (and `computeCartLineUnitPrice`) **per cart line** with `await` inside the loop. Fine for small carts; batch the lookups (`inArray`) if carts can grow. Note the checkout logic itself is correct — prices are recomputed server-side and price/availability drift blocks the order.
- Rate-limit counters run `count(*)` over `signInAttempts` on every request. Works, but a hot path against an ever-growing table; ensure an index on `(email, reason, createdAt)` / `(ip, reason, createdAt)` and prune old rows.
- Ownership note: `loadMeasurementSnapshot` / made-to-measure validation don't verify the measurement profile belongs to the current user/anon — low impact (own data), worth tightening.
