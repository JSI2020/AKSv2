## STEP 21 — Catalog schema & admin CRUD

**Goal:** designs exist and can be entered by hand. No AI.

**Prompt:**
> Create schema:
> - `designs` — id, slug unique, name, nameUr, description, storyCopy, status (DRAFT|PUBLISHED|ARCHIVED), garmentType FK, components jsonb, sizeBlockId FK, fitProfileIds jsonb, basePriceMinor, madeToMeasureSurchargeMinor, fabricConsumptionMeters, leadTimeDaysOverride, featured, publishedAt, archivedAt, seoTitle, seoDescription
> - `design_tags` — designId, kind (OCCASION|SEASON|WORK|FREE), value
> - `colourways` — id, designId, name, nameUr, slug, fabricId FK, hexApproximation, priceDeltaMinor, isDefault, sortOrder, active
> - `design_renders` — id, designId, colourwayId, angle (FRONT|THREE_QUARTER|BACK|DETAIL), archetypeId nullable, assetId, **isAiGenerated default false**, altText, sortOrder
> - `customization_options` and `customization_option_values` with priceDeltaMinor and referenceAssetId
>
> **`design_renders` must be image-source agnostic** — a render is an asset attached to a colourway and angle, whether uploaded manually now or generated by the Design Studio in step 42. No consumer should be able to tell the difference.
>
> Seed tag values: OCCASION (CASUAL, EVERYDAY, FORMAL, SEMI_FORMAL, FESTIVE, PARTY, EVENING, EID, WEDDING_GUEST, MEHNDI, BARAAT, WALIMA, NIKAH, BRIDAL, OFFICE), SEASON (SUMMER, WINTER, SPRING, AUTUMN, MID_SEASON, FESTIVE, WEDDING), WORK (EMBROIDERED, PRINTED, PLAIN, HAND_EMBELLISHED, ZARI, ZARDOZI, SEQUIN, BLOCK_PRINT, DIGITAL_PRINT, MIRROR_WORK).
>
> Build admin CRUD at `/admin/designs` and `/admin/designs/[id]` with tabs: Details, Media, Colourways, Pricing, Sizing, Customization. Manual image upload per colourway × angle using step 9's asset module. **Alt text is required before publish.** Every selection — category, fabric, size block, fit profile, tags — is a searchable dropdown, never free text.

**Exit:** you create one design by hand with two colourways and three angles each, and it saves.

## STEP 23 — Collection & filtering

**Goal:** browse and filter designs.

**Prompt:**
> Build `/collections/[slug]` per the prototype design. Server-render a faceted grid of published designs. Filters: occasion, garment type, fabric, work type, price range. **Filter state lives in the URL via nuqs** so it is shareable and back-button correct.
>
> Implement these query functions in `/modules/catalog`: `getPublishedDesigns(filters, sort, page)` and `resolveCollection(slug)` — the latter must handle both attribute-filter slugs and computed system collections.
>
> Implement computed collections as database views or cached queries, **never as manual tags**: new arrivals (publishedAt within 30 days), best sellers (ranked by paid order_items over a trailing window — paid, not merely placed). If you find yourself adding a "mark as best seller" checkbox, that is the bug.

**Exit:** filtering by occasion updates the grid and the URL; sharing that URL reproduces the filtered view.

## STEP 24 — Product detail page

**Goal:** the page where the sale happens.

**Prompt:**
> Build `/designs/[slug]` per the prototype.
>
> Implement `resolveImages(designId, colourwayId)` returning `{ FRONT, THREE_QUARTER, BACK }` from `design_renders`. **This reads cached rows only and never generates anything.**
>
> Build a single configurator state object that owns: angle, colourwayId, sizeMode, sizeLabel, measurements, quantity. Every control writes to it; every visual reads from it. Sync the durable parts to the URL with nuqs. Any modal opens *over* the page — never a navigation — so nothing unmounts and no selection resets.
>
> Angle switching: hover zones on desktop, swipe plus thumbnails on mobile, cross-dissolve between images, all three angles preloaded for the current colour. Colour switching: swap to that colourway's cached images instantly, keeping the current angle. Show fabric swatch macros, not flat colour dots.
>
> Also render: price via `<Money>`, honest lead time, fabric story link, and the model disclosure string from step 19.

**Exit:** changing colour is instant and preserves the current angle; refreshing the page restores colour and angle from the URL.

## STEP 25 — Size selection & guide

**Goal:** choose a standard size with confidence.

**Prompt:**
> Add size selection to the product page: XS–XXL buttons plus a "Made to measure" option, and a "Size guide" button beside them.
>
> The size guide opens as a modal over the page. It shows the measurement table for this design's garment type, resolved from its size block via `resolveChart` — grouped by component when the design has several (shirt rows, trouser rows, dupatta rows). Display **body measurements by default** ("fits a bust of 36–38″"), since that is what a customer can measure on herself, with a toggle to finished-garment measurements.
>
> All values render through `<Measure>`. Selecting a size in the guide applies it and closes the modal, leaving every other configurator selection intact.

**Exit:** the size guide shows correct per-component measurements for a 3-piece design, and choosing a size there applies it to the page without resetting colour or angle.

## STEP 26 — Custom measurement flow

**Goal:** the made-to-measure path, with validation that keeps garments producible.

**Prompt:**
> First create `custom_size_limits` (categoryId, measurementKey, minValue, maxValue, step default 25, crossFieldRules jsonb) with admin CRUD, seeded with: BUST 30–52, WAIST 22–48, HIP 32–56, SHOULDER 12–20, SLEEVE_LENGTH 0–26, kameez LENGTH 26–52, TROUSER_LENGTH 32–46 (inches).
>
> Build `/designs/[slug]/measure` — a resumable multi-step flow, one measurement per screen, autosaving every field to the server so a refresh never loses sixteen measurements. Each field shows a help text and a demo video slot.
>
> Validate in three layers, server-side as source of truth: per-measurement min/max; snap to 0.25″; cross-field plausibility (HIP ≥ WAIST, SLEEVE_LENGTH ≤ LENGTH). **Plausibility violations prompt rather than block** unless physically impossible — copy per `/docs/AKS_Brand_Foundation.md`, e.g. "A 30″ bust with a 44″ waist is unusual — worth checking the tape once more."
>
> End with a review screen: a plain-language spec summary, the ±0.5″ tolerance note, and an explicit acknowledgement that made-to-measure garments are made to her specification and are not returnable. Checked deliberately, not a link.
>
> Also create `customer_measurement_profiles` and `customer_measurements` so a signed-in customer can save and reuse a profile.

**Exit:** you complete all measurements on a phone, refresh mid-flow and lose nothing, and an implausible value prompts rather than blocking.

## STEP 27 — Cart

**Goal:** a cart that survives.

**Prompt:**
> Create `carts` (id, userId nullable, anonId, status, expiresAt) and `cart_lines` (id, cartId, designId, colourwayId, sizeMode, sizeLabel nullable, measurementProfileId nullable, customizationSelections jsonb, unitPriceMinor, quantity).
>
> **The cart is server-side**, keyed by an httpOnly `anonId` cookie for guests, merging into the user's cart on sign-in. No browser-storage-only cart.
>
> Add-to-cart snapshots the configurator state and **computes the price server-side** — never trust a client-supplied price. Pricing formula: `basePrice + colourwayPriceDelta + Σ(customizationDeltas) + (madeToMeasure ? surcharge : 0)`.
>
> Build the cart drawer per the prototype: line items with thumbnail, colour, size or "Made to measure", quantity stepper, unit and line price, remove. Show subtotal and lead time. Add-to-cart is optimistic and reconciles on the server response.

**Exit:** add two items on your phone, close the browser, reopen — the cart is intact with correct prices.

## STEP 28 — Checkout & Pakistani address

**Goal:** guest checkout that fits how addresses actually work here.

**Prompt:**
> Build the checkout flow per the prototype: address → payment plan → review → place order. Guest checkout is allowed; offer account creation only *after* the order is placed, never as a gate before it.
>
> Create `addresses` with **Pakistani format**: recipientName, phone, addressLine1 (house/flat, street), addressLine2 (area, block, sector), city, province (select: Punjab, Sindh, KPK, Balochistan, Gilgit-Baltistan, AJK, ICT), postalCode **optional**, and a **landmark** field — that is how addresses work in practice here. Do not build a postcode-lookup-centric form.
>
> Capture a WhatsApp number explicitly, labelled as how order updates will arrive.
>
> Payment plan selection with the deposit rule stated in plain language, not a tooltip: standard sizes may use 50% deposit with balance on delivery; made-to-measure requires 70% deposit or full prepayment, because a garment cut to one customer's measurements cannot be resold. State that the deposit is non-refundable once cutting begins.
>
> Re-validate at checkout: design still published, price unchanged. If anything changed, say so plainly before payment.

**Exit:** you complete checkout as a guest with a real Pakistani address; a made-to-measure line refuses the 50/50 plan.

## STEP 29 — Orders schema & state machine

**Goal:** the spine, with immutable snapshots.

**Prompt:**
> Create:
> - `orders` — id, orderNumber (human readable, format `AKS-2026-00001`), userId nullable, guestEmail, guestPhone, whatsappNumber, status, currency PKR, subtotalMinor, discountMinor, shippingMinor, taxMinor, totalMinor, depositAmountMinor, balanceAmountMinor, paymentPlan, promisedShipDate, **shippingAddressSnapshot jsonb**, customerNotes, internalNotes, source (WEB|WHATSAPP|INSTAGRAM|PHONE|WALK_IN), placedAt, cancelledAt, cancelReason
> - `order_items` — id, orderId, designId, colourwayId, **designSnapshot jsonb**, sizeMode, sizeLabel, **measurementSnapshot jsonb**, **customizationSnapshot jsonb**, **priceBreakdownSnapshot jsonb**, **cutSpecSnapshot jsonb**, unitPriceMinor, quantity, lineTotalMinor
> - `order_events` — append-only
>
> **Every field marked snapshot is a frozen copy, never a foreign key.** If the customer later edits her measurement profile, or the designer changes a price, existing orders must not change. This is the difference between winning and losing a dispute three weeks later.
>
> Order state machine, implemented through step 7's `transition()`:
> `DRAFT → AWAITING_DEPOSIT → DEPOSIT_PAID → MEASUREMENTS_CONFIRMED → IN_PRODUCTION → QUALITY_CHECK → READY_TO_SHIP → DISPATCHED → DELIVERED → COMPLETED`
> Side exits: `CANCELLED` (only before MEASUREMENTS_CONFIRMED), `REFUND_PENDING → REFUNDED`, `DELIVERY_REFUSED → WRITE_OFF`.
>
> Cancellation after MEASUREMENTS_CONFIRMED forfeits the deposit and requires an explicit reason. Compute `cutSpecSnapshot` at order placement using step 20's calculator.
>
> Tests: an illegal transition throws; editing a design's price does not alter an existing order.

**Exit:** checkout produces an order with a readable number and frozen snapshots; the immutability test passes.

## STEP 30 — Admin order list & detail

**Goal:** run orders from the portal.

**Prompt:**
> Build `/admin/orders` (list) and `/admin/orders/[id]` (detail), following the table patterns in `/reference/next-shadcn-dashboard-starter`.
>
> List columns: order number, customer, date, **production status**, **payment status**, total, promised date, at-risk flag. Filters URL-synced via nuqs. Saved views.
>
> **Production status and payment status are two independent fields.** An order can be "stitching" and "balance due" simultaneously. Never combine them into one.
>
> Detail shows: customer with link, the full shipping address snapshot, items with the immutable measurement snapshot displayed as a table, customization selections, price breakdown, payment state, production stage, an append-only event timeline, and internal versus customer-visible notes clearly separated.
>
> Actions, each permission-gated: confirm measurements, advance stage, record payment, refund, cancel with reason (from a dropdown of reason codes), edit before production lock, adjust price with a reason. Add photo upload per stage with a flag for whether the customer sees it.

**Exit:** an order placed on the storefront appears in admin with its exact measurement snapshot; a STAFF user cannot refund.

**Prompt:**

## STEP 32 — Payments: interface & Safepay

**Goal:** take money, safely.

**Prompt:**
> **Stripe does not support merchants in Pakistan — do not architect around it.**
>
> Create `payments` (id, orderId, provider, providerRef, kind DEPOSIT|BALANCE|FULL|REFUND, amountMinor, currency PKR, status, rawPayload jsonb, **idempotencyKey unique**, receiptAssetId, verifiedById, verifiedAt) and `refunds`.
>
> Define a `PaymentProvider` interface with `createCheckout`, `verifyWebhook`, `refund`, `getStatus`. Implement a Safepay adapter behind it. **Check Safepay's current API documentation for exact request and response shapes — do not invent them.** No provider SDK may be imported outside `/modules/payments/providers/`.
>
> Webhook handler: verify the signature, deduplicate on `idempotencyKey`, record the raw payload, transition the order via `transition()`, emit an outbox message. **A webhook delivered five times must produce exactly one payment row and one transition.** Write that test explicitly.

**Exit:** a test deposit transitions the order to DEPOSIT_PAID; replaying the webhook five times creates one payment record.

## STEP 33 — Bank transfer & COD

**Goal:** the two payment methods this market actually uses.

**Prompt:**
> **Bank transfer** — the customer selects it, sees account details with the order number as reference, and uploads a receipt image. The order sits at an awaiting-verification state. Build an admin queue at `/admin/payments/verification` showing the receipt beside the expected amount, with one-click verify or reject-with-reason. Verification transitions the order and emits notifications.
>
> **COD** — record the balance as collected on delivery. Create `cod_remittances` (courier, remittanceRef, expectedAmountMinor, receivedAmountMinor, receivedAt, orderIds array, discrepancyNote) with manual entry, matching against delivered orders and flagging discrepancies. Build an outstanding-COD report — couriers typically remit days after delivery, so this is real cash-flow exposure.
>
> Add `codRefusalCount` to the customer record; a delivery refusal increments it and automatically disables COD for that customer on future orders.

**Exit:** you verify a bank transfer from the admin queue and the order advances; a refused delivery disables COD for that customer.

## STEP 34 — Status pipeline & automatic notifications

**Goal:** the customer is informed without anyone remembering to tell them.

**Prompt:**
> Add the production pipeline to orders, with fixed stages: Received → Confirmed → Measurements verified → Cutting → Stitching → Embroidery (skipped automatically when the design has no embroidery work tag) → Finishing → Quality check → Packed → Dispatched → Delivered → Completed.
>
> **Cutting cannot be entered unless the order is at MEASUREMENTS_CONFIRMED.** Enforce in the state machine, not the UI. Once cloth is cut to a customer's measurements it cannot become anyone else's garment.
>
> Every status change: **automatically** sends the customer an email via Resend through the outbox, and updates their order view. Admin adds an optional remark with each change; internal remarks are never sent.
>
> Create `message_templates` (key, channel, locale, version, subject, body) and `message_log` (recipient, templateKey, status, providerRef, sentAt, error) with retry from admin. Write templates in the AKS voice per `/docs/AKS_Brand_Foundation.md` — plain, warm, second person. Leave Urdu template bodies empty rather than machine-translating; fall back to English.
>
> Build customer-facing order tracking: `/account/orders/[orderNumber]` for signed-in users, `/track/[orderNumber]` gated by email OTP for guests. Show the production timeline as steps, not a bare status label.

**Exit:** you change a status in admin; the customer email arrives without any further action, and the tracking page reflects it.
